# Рекомендации и приоритизация мер

## 1. Подход к приоритизации

Приоритет определяется по двум критериям:
- влияние на устойчивость и производительность;
- срочность внедрения до активной миграции.

Используются уровни:
- **P1 — критично**
- **P2 — важно**
- **P3 — желательно**

---

## 2. Список мер

| Приоритет | Мера | Что устраняет |
|---|---|---|
| P1 | Выделить отдельный трек миграции данных (inventory, mapping, dedup, quality rules) | Узкие места данных, несогласованность old/new |
| P1 | Спроектировать target data model и master record пациента | Дубли, расхождения CRM / медданных / биллинга |
| P1 | Выполнить capacity planning на период двойного контура | Узкие места по CPU, RAM, IOPS, network |
| P1 | Ввести API Gateway и отдельные integration adapters | Узкие места на стыке с лабораторией, 1С и партнерами |
| P1 | Исключить shared database как способ интеграции сервисов | Блокировки, coupling, деградация производительности |
| P1 | Сформировать базовый observability stack: metrics, logs, tracing, SLI/SLO | Невозможность быстро находить bottleneck |
| P1 | Выбрать поэтапный cutover вместо big bang | Снижение риска массового отказа |
| P2 | Перевести длительные интеграционные процессы на async / queue-based модель | Блокировки пользовательских сценариев |
| P2 | Ввести кэширование справочников, расписаний, редко меняющихся данных | Избыточная нагрузка на БД и сервисы |

## 3. Практические рекомендации по категориям

## 3.1 Данные
1. Провести полную инвентаризацию источников данных.
2. Выделить canonical model для пациента, записи, услуги, платежа и медсобытия.
3. Подготовить migration pipeline:
   - извлечение;
   - очистка;
   - нормализация;
   - дедупликация;
   - валидация;
   - обратная сверка.
4. Для периода перехода реализовать controlled synchronization, а не ручной двойной ввод.

**Приоритет: P1**

---

## 3.2 Инфраструктура
1. Выполнить оценку ожидаемой нагрузки с учетом x5 роста и dual-run периода.
2. Разделить контуры:
   - production data services;
   - observability;
   - integration services;
   - аналитика.
3. Отдельно оценить storage profile:
   - БД;
   - документы;
   - логи;
   - бэкапы.
4. Подготовить DR и backup strategy до начала cutover.

**Приоритет: P1**

---

## 3.3 Приложения и сервисы
1. Строить декомпозицию вокруг бизнес-доменов, а не вокруг UI-экранов.
2. Для критичных пользовательских сценариев ограничить число синхронных hops.
3. Использовать паттерны:
   - cache aside;
   - circuit breaker;
   - retry with backoff;
   - idempotency.
4. Не делать "микросервисы ради микросервисов": допустим modular monolith на первом этапе,
   если команда пока мала.

**Приоритет: P1/P2**

---

## 3.4 Интеграции
1. Изолировать лабораторию и 1С за integration adapters.
2. Для ненадежных или медленных систем применять очереди.
3. Установить SLA/SLO для внешних вызовов.
4. Для пользовательских сценариев предусмотреть статусную модель:
   "запрос принят", "результат ожидается", "уведомление отправлено", а не блокирующее ожидание.

**Приоритет: P1/P2**

---

## 3.5 Персонал и процессы
1. Назначить владельцев доменов и сервисов.
2. Подготовить runbooks и инструкции на инциденты.
3. Провести обучение ресепшена, врачей и кассиров новым процессам.
4. Выделить ресурс на операционную поддержку периода миграции.

**Приоритет: P2**

---

## 3.6 Наблюдаемость
1. Метрики на пользовательские сценарии:
   - запись к врачу;
   - создание/подтверждение приема;
   - получение результатов лаборатории;
   - оплата;
   - доставка уведомления.
2. Distributed tracing на межсервисные вызовы.
3. Dashboard по bottleneck-метрикам:
   - latency;
   - error rate;
   - queue lag;
   - DB saturation;
   - external API latency.
4. Alerting не только по инфраструктуре, но и по бизнес-сценариям.

**Приоритет: P1**

---

## 4. Предлагаемая последовательность работ

### Этап 1. До активной разработки
- инвентаризация данных и систем;
- целевая доменная модель;
- архитектурные решения по интеграциям;
- observability baseline;
- capacity planning.

### Этап 2. Пилотный контур
- запуск ограниченного набора сервисов;
- миграция части клиентского потока;
- нагрузочное тестирование;
- проверка операционной модели.

### Этап 3. Controlled rollout
- поэтапный перевод филиалов / процессов;
- контроль метрик;
- исправление bottleneck по мере роста нагрузки.

### Этап 4. Вывод legacy
- отключение ручных обходов;
- завершение миграции архивов;
- cleanup и оптимизация.

---

## 5. Итоговый вывод

Для данной компании основные bottleneck находятся не только в коде, а в сочетании:
- legacy-данных,
- интеграций,
- ограниченной инфраструктуры,
- малой команды,
- отсутствия зрелой observability и target operating model.

Поэтому приоритетной мерой является **не просто начать разрабатывать микросервисы**, а сначала
подготовить контролируемую архитектурную и операционную базу миграции.
