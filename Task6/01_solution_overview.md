# Общее проектное решение

## 1. Постановка задачи

В целевой архитектуре компании «Медикаменте» требуется построить аналитический контур для BI, ML и AI.
При этом источники данных обладают следующими свойствами:

- данные приходят из разных систем: CRM, booking, medical, billing, notifications, лабораторная интеграция, 1С;
- входные структуры изменяются со временем (schema drift);
- данные не размечены по классам конфиденциальности;
- в потоке присутствуют поля, содержащие персональные данные, медицинскую тайну, финансовую информацию и внутренние операционные сведения;
- часть данных допустимо использовать в аналитике только после обезличивания или псевдонимизации.

Из этого следует, что загрузка данных в аналитическое хранилище не может быть прямой.
Между источниками и аналитическим storage должен быть добавлен отдельный слой классификации и privacy-processing.

---

## 2. Принципиальный подход

Предлагается ввести **Data Classification & Privacy Processing Layer** как отдельный слой в аналитической архитектуре.

Этот слой выполняет четыре основные функции:

1. **Schema discovery и profile analysis**
   - анализирует новые таблицы, файлы, JSON-сообщения и API payload;
   - определяет структуру набора данных;
   - выявляет schema drift и изменения состава атрибутов.

2. **Data classification**
   - присваивает класс данным и отдельным полям;
   - использует правила, словари, pattern matching, ML/heuristics;
   - определяет уровень чувствительности и допустимые способы обработки.

3. **Privacy transformation**
   - применяет masking, tokenization, pseudonymization, anonymization;
   - обрезает избыточные поля;
   - формирует privacy-safe представления данных.

4. **Routing и governance**
   - направляет данные в соответствующий слой аналитического хранилища;
   - сохраняет metadata, tags, lineage, quality signals, policy decisions;
   - не допускает загрузки наборов данных без классификации.

---

## 3. Почему нужен отдельный слой, а не просто правила в ETL

Обычный ETL-процесс недостаточен, потому что:
- правила должны работать для меняющихся схем;
- классификация должна быть централизованной и повторно используемой;
- нужны единые policy decisions для BI / ML / AI;
- требуются наблюдаемость, метрики качества классификации, lineage и аудит;
- privacy-трансформации должны быть отделены от бизнес-логики ingestion.

---

## 4. Принципы Privacy by Design в решении

### Privacy as Default
По умолчанию ни один новый набор данных не попадает в аналитическое хранилище без классификации и policy check.

### Data Minimization
В analytics pipeline передаются только необходимые атрибуты; избыточные поля отбрасываются или маскируются.

### Purpose Limitation
Разные аналитические сценарии (BI, ML, LLM, ad hoc analysis) получают разные представления данных.

### End-to-End Protection
Контроль распространяется на ingestion, staging, transformation, storage, access и deletion.

### Transparency and Auditability
Каждое решение классификатора, каждое правило и каждый маршрут загрузки должны быть трассируемы.

---

## 5. Вывод

Целевое решение должно включать не просто data lake / DWH, а **privacy-aware analytical platform**,
в которой классификация данных является обязательным архитектурным этапом перед загрузкой.
