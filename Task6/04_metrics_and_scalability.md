# Метрики эффективности классификации и масштабируемость

## 1. Метрики эффективности классификации

Для оценки эффективности движка классификации необходимо использовать не одну, а несколько групп метрик.

## 1.1 Качество классификации

### Precision
Доля корректно классифицированных чувствительных полей среди всех полей, которые движок отметил как чувствительные.

**Зачем нужна:**  
Позволяет понять, насколько часто система даёт false positives.
Если precision низкая, аналитика будет получать чрезмерно "зажатые" данные, а команда — лишние ручные проверки.

### Recall
Доля реально чувствительных полей, которые движок сумел обнаружить.

**Зачем нужна:**  
Это одна из главных privacy-метрик.
Если recall низкая, чувствительные данные могут попасть в аналитическое хранилище без нужной защиты.

### F1-score
Баланс между precision и recall.

**Зачем нужна:**  
Даёт агрегированную оценку, особенно полезную при сравнении разных версий классификатора.

### Confidence distribution
Распределение confidence score по наборам данных и полям.

**Зачем нужна:**  
Позволяет понимать, где движок работает надёжно, а где требуется rule tuning или manual review.

---

## 1.2 Операционные метрики

### Classification latency
Время классификации набора данных до решения policy engine.

**Зачем нужна:**  
Если latency высока, batch ingestion начнёт тормозить весь аналитический pipeline.

### Throughput
Количество наборов / файлов / таблиц / сообщений, которые движок может обработать за единицу времени.

**Зачем нужна:**  
Показывает, выдерживает ли система объём пакетных загрузок.

### Schema drift detection rate
Доля изменений схемы, которые были обнаружены автоматически.

**Зачем нужна:**  
Показывает способность движка адаптироваться к evolving schemas.

### Manual review rate
Доля наборов, отправленных на ручную валидацию.

**Зачем нужна:**  
Если показатель слишком высок, система плохо масштабируется организационно.

### Quarantine rate
Доля наборов, помещённых в quarantine.

**Зачем нужна:**  
Позволяет отслеживать качество входных данных и корректность правил.

---

## 1.3 Governance и privacy-метрики

### Sensitive field leakage rate
Количество чувствительных полей, попавших в неразрешённый слой или dataset.

**Зачем нужна:**  
Это ключевая метрика риска.

### Policy violation count
Число нарушений privacy-политик, обнаруженных на этапе загрузки или доступа.

### Dataset coverage
Доля аналитических наборов, для которых есть:
- owner;
- classification;
- tags;
- lineage;
- retention policy.

### Re-identification risk score
Оценка вероятности восстановления личности в anonymized layers.

**Зачем нужна:**  
Критична для BI/ML/AI зон.

---

## 2. Как метрики помогут оптимизировать систему

Метрики нужны не только для контроля качества, но и для оптимизации:

- **низкий precision** → нужно сократить false positives, доработать словари и правила;
- **низкий recall** → нужно усилить обнаружение чувствительных данных, особенно текстовых и новых полей;
- **высокий manual review rate** → нужно улучшать классификатор и автоматизировать rule coverage;
- **высокая latency** → нужно масштабировать engine, оптимизировать profiling и ML-inference;
- **рост quarantine rate** → нужно улучшать data contracts со стороны источников;
- **рост re-identification risk** → нужно усиливать anonymization techniques.

## 3. Масштабируемость решения

## 3.1 Принципы scalability

Для обеспечения масштабируемости движок должен проектироваться как stateless и horizontally scalable сервис.

### Основные принципы
- независимые worker-ноды для batch-классификации;
- асинхронная orchestration модель;
- отделение control plane от data plane;
- кэширование часто используемых словарей и правил;
- возможность шардировать обработку по источникам, датасетам или партициям.

---

## 3.2 Что нужно масштабировать

### Ingestion / connectors
При росте числа источников нужно иметь возможность подключать новые коннекторы без изменения ядра системы.

### Profiler и classifier workers
Это основной вычислительный bottleneck. Масштабируются горизонтально по batch-job'ам.

### Metadata / catalog layer
Нужна оптимизация по объёму lineage, версионированию схем и search / lookup нагрузке.

### Storage layers
Рост объёма данных потребует:
- partitioning;
- lifecycle management;
- tiered storage;
- оптимизации форматов хранения.

---

## 3.3 Как расширять систему

При увеличении объёма данных или числа пользователей следует предусмотреть:

1. **Горизонтальное масштабирование worker pool**
   - отдельные очереди задач;
   - autoscaling по backlog и processing latency.

2. **Разделение классификации по типам данных**
   - structured pipeline;
   - semi-structured pipeline;
   - document/text classification pipeline.

3. **Версионирование правил и моделей**
   - чтобы обновление классификатора не ломало воспроизводимость.

4. **Модульное подключение новых detectors**
   - новые regex detectors;
   - новые domain dictionaries;
   - новые ML-модели.

5. **Разделение аналитических зон по бизнес-направлениям**
   - если количество пользователей и объём запросов вырастут кратно.

6. **Semantic access layer / governed data products**
   - для большого числа BI и ML-потребителей.

---

## 4. Итоговый вывод

Эффективность движка классификации должна оцениваться одновременно по:
- качеству определения чувствительных данных;
- операционной производительности;
- governance-покрытию;
- privacy-risk показателям.

Масштабируемость должна закладываться изначально:
не как масштабирование одного ETL-скрипта, а как масштабирование целого privacy-aware platform layer.
